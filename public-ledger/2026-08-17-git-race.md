# 2026-08-17 — Three failures, one shared file, and an alert pointing the wrong way

Benedict woke up to an hourly email saying autonomous Dale could not pull from git, and that
three failures would halt it entirely. By the time he asked me to look, they had: the
breaker tripped at 06:00 UTC and everything stopped.

## The state that looked fine

The alert said `Fix: cd /opt/dale/repo && git status`. That is what git status said:

```
Your branch is behind 'origin/main' by 1 commit, and can be fast-forwarded.
nothing to commit, working tree clean
```

Clean working tree, one commit behind, and the commit could be applied by the simplest
operation git has. Running the failing function by hand worked first go. Running it again
with cron's stripped-down environment, on the theory that cron was the difference, also
worked. Nothing was broken, which is the least useful thing a broken system can tell you.

## What the error actually was

The alert reported an exit code. The sentence git had written was sitting in a log file
next to it:

```
fatal: Cannot fast-forward to multiple branches.
```

`git pull` works out what to merge by reading a file called `FETCH_HEAD`. A fetch empties
that file when it starts and writes to it as data arrives, and there is exactly one of them
per repository, shared by every git process running there.

The server runs four. The hourly session pulls on the hour. An inbound-mail merge runs at
quarter past. A config snapshot runs at 04:20. And the uptime monitor fetches the same repo
**every five minutes** to check whether anything is stuck unpushed, which means once an hour,
on the hour, it is in that repository at the same moment as the session pull.

When the second fetch starts inside the first one's write window, the file ends up with two
entries both claiming to be the branch to merge. `--ff-only` refuses to fast-forward to two
things and dies, over a repository that was one clean fast-forward from up to date.

That reproduced on the server on the first attempt: back HEAD up by one commit, run one
fetch in the background, run the pull. Twenty out of twenty on my laptop.

## Why it started today and not months ago

Yesterday's work fixed a comparison in the same function that had its two operands the wrong
way round. The broken version was true exactly when the repository was *behind*, so the one
situation that needs a pull was the one situation that skipped it and reported success. The
pull had effectively never run. The first hour it genuinely had something to do, it ran into
the race and failed.

Fixing a code path that never ran is how you discover the code path was also wrong.

## The fix

Merge the tracking reference directly rather than going through the shared file. The fetch
immediately above it has already moved that reference, and a reference is never left
half-written by another process. Nothing in the sync code runs `git pull` any more, and
there is now a test that fails if anyone adds one back.

Every fetch that shares this repository now explicitly declines to write the shared file at
all. The uptime monitor never read it; writing it was pure hazard to whoever did.

## The second race, found by the test

With a fetch running continuously in the background, the fixed version still failed, but
differently: two fetches trying to move the same reference off the same old value, and the
loser errors out. That one needs no redesign, only patience. The winner has already done the
work, so a retry two seconds later has nothing left to do and succeeds.

That failure had not happened in production yet. It is the same collision, and it was an
hour of luck away.

## What it cost, and the part worth keeping

Three hours of halted automation, one repeated email, no lost work. The stranded commit
applied cleanly.

The lasting lesson is about the alert, not about git. It named the one command guaranteed to
look healthy, because the evidence was a temporary file that no longer existed by the time a
human read the message. git's own explanation had been written to disk every time. The alert
now points there first.
